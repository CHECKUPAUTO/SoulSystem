# SoulSystem Security Invariants

This document lists the invariants the production hardening effort must
establish and keep true. Each invariant is stated so that it can be checked by
a test or a reproducible command. An invariant is only considered **held** once
a test proves it; until then it is **target**.

Status legend: `HELD` (proven by a test in-tree) · `PARTIAL` (partially
enforced) · `TARGET` (not yet enforced).

The PR column refers to the [production hardening plan](PRODUCTION_HARDENING_PLAN.md)
PR sequence (A–P).

## Startup and mode

| ID | Invariant | PR | Status |
|----|-----------|----|--------|
| INV-ENV-1 | The runtime mode is decided only from an explicit `SOULSYSTEM_ENV` value; production is never inferred from the absence of a flag. | A | HELD (`soul-prod-guard`: `mode_unset_is_error`, `mode_unknown_is_error`) |
| INV-ENV-2 | In production, any single unmet security prerequisite aborts startup before any listener opens (fail closed). | A | HELD (`soul-prod-guard`: per-violation rejection tests) |
| INV-ENV-3 | No secret value ever appears in a guard violation, audit event, or startup error. | A | HELD (`violation_display_carries_no_secret_values`, `rejected_error_message_is_stable_and_secret_free`) |

## Tool dispatch and execution

| ID | Invariant | PR | Status |
|----|-----------|----|--------|
| INV-TOOL-1 | An unregistered tool name can only produce `UnknownTool`; it can never reach process execution. | B | HELD (`soul_tools`: `unknown_tool_never_executes`, `malformed_tool_names_rejected`) |
| INV-TOOL-2 | Every tool has a trusted, statically-registered capability that the caller cannot downgrade. | C | HELD (`soul_tools`: `write_tools_are_not_classified_as_read`, `capability_classification_is_trusted_and_correct`) |
| INV-EXEC-1 | No production-reachable code path invokes `std::process::Command` / `tokio::process::Command` / `libc::exec*` outside the single approved sandbox executor. | D/N | PARTIAL (`soul_tools::execute_shell` — the agent dispatch path, and the `execute_tool` helper that calls it — now route through `soul_sandbox`; `execute_shell_routes_through_sandbox` test. Within `soul_sandbox` itself, `execute_with_stdin` previously built its own `Command` with only `setpgid` in `pre_exec`, bypassing seccomp/network isolation entirely — fixed in D-2 by routing it through the same `apply_sandbox_pre_exec` helper as `execute()`; `execute_with_stdin_also_gets_network_isolation_when_the_host_permits_it`. N: `AutonomousAgent::executor` — an `AsyncShellExecutor` field constructed but never referenced (confirmed via `grep -n "self.executor" soul-agent-core/src/` returning zero matches before removal), sitting beside the real dispatch path and implying a second, unused sandboxing mechanism existed — removed entirely (field, import, both constructor sites); `run_react_dispatch_path_is_sandboxed_for_destructive_commands` calls the exact `async_dispatch_tool` function `run_react`'s tool-dispatch loop calls, not a mock, and asserts it refuses a destructive command end-to-end. A repo-wide architecture ban on bare `Command` outside `soul_sandbox` is still open, tracked as PR D-3/N-2.) |
| INV-EXEC-2 | Process tools fail closed when the mandatory OS isolation backend is unavailable in production. | A/D-2 | HELD for seccomp only (`soul_sandbox`: `pre_exec` propagates `install_filter` failure via `Err`, aborting the fork before `exec()`; `unknown_seccomp_profile_fails_closed_refuses_to_execute`). `SECCOMP_SET_MODE_FILTER` itself requires either `CAP_SYS_ADMIN` or `no_new_privs` (seccomp(2)) — a second CI-discovered gap: `apply_sandbox_pre_exec` now sets `PR_SET_NO_NEW_PRIVS` unconditionally before `install_filter`, so seccomp installs (and its fail-closed guarantee holds) for an unprivileged caller too, not just root; verified by running the full `soul_sandbox` suite under `setpriv --reuid nobody`, not just as root. Network-namespace setup is deliberately *not* fail-closed — see INV-EXEC-3; a genuine environmental unavailability (as opposed to a config error) degrades gracefully rather than blocking all execution. Mount/PID namespace and cgroup setup have no isolation to fail closed on yet — deferred to PR D-3. |
| INV-EXEC-3 | Process tools have no network access by default; egress is per-tool allowlisted. | D-2 | PARTIAL, best-effort (`soul_sandbox::SandboxPolicy::default().network_isolated == true`; the sandboxed process attempts to run in its own network namespace with no interfaces via `unshare(CLONE_NEWUSER\|CLONE_NEWNET)` in `pre_exec`). Discovered via PR #84 CI red on a standard GitHub Actions Ubuntu runner: many common unprivileged Linux hosts (Ubuntu 23.10+'s default AppArmor policy restricts unprivileged `CLONE_NEWUSER`) cannot create a network namespace at all, regardless of root/unprivileged — treating that as fail-closed would make the sandbox refuse to run *any* command on those hosts. `apply_sandbox_pre_exec` now logs and continues without network isolation (seccomp still applies) when `unshare` fails, verified with `default_policy_has_mandatory_isolation_active` (policy intent) and `network_isolated_gets_a_fresh_network_namespace_when_the_host_permits_it` / `network_not_isolated_shares_host_namespace_when_disabled` (isolation actually takes effect where the host allows it; command execution never blocks either way). Per-tool egress allowlisting (as opposed to all-or-nothing) is not implemented — noted as a follow-up. |
| INV-EXEC-4 | Process output and CPU/memory/pids/fd/time are bounded; the process group is killed on timeout. | D-2 | PARTIAL (output: `SandboxPolicy::max_output_bytes` caps stdout/stderr capture via `read_capped`, default 2 MiB; `output_is_capped_to_max_output_bytes`. Time: pre-existing `policy.timeout` + `killpg(SIGKILL)` on the process group, unchanged. CPU/memory/pids/fd limits via cgroups are TARGET — PR D-3.) |
| INV-EXEC-5 | There is exactly one agent runtime abstraction reachable from the `soulsystem` binary's entry points — no simultaneous `AutonomousAgent` + `SoulEntity` + `soul-kernel` execution paths with independent security postures. | N | TARGET (HIGH-008's narrower, low-risk sub-issue — the dead `AutonomousAgent::executor` field implying a second sandboxing mechanism — is fixed above under INV-EXEC-1. The broader claim here is NOT addressed: `src/main.rs` still dispatches to `AutonomousAgent` (`--daemon`) and `SoulEntity` (`--entity`) as genuinely separate runtimes with separate memory/sandbox abstractions, `soul-kernel` remains an independent `[[bin]]` with its own LLM/memory/state, and `clawd::run_bot` / the `soul_gateway` Telegram provider can both poll the same bot token. Consolidating these is a large, product-affecting architectural decision — which runtime is canonical, whether `--entity`/standalone `soul-kernel` are still needed — deliberately not attempted unilaterally in an autonomous pass; needs explicit product direction before implementation.) |

## Planner and autonomy

| ID | Invariant | PR | Status |
|----|-----------|----|--------|
| INV-PLAN-1 | Planner history records the actual tool outcome (`success == actual result`). | I | HELD (`soul-agent-core`: `record_tool_outcome` passes real `tool_ok`, not a hardcoded literal, to `planner.history.record`; `planner_history_records_actual_outcome_not_hardcoded_success`, `planner_history_all_failures_yields_zero_success_rate`) |
| INV-PLAN-2 | Autonomous execution has hard budgets (turns, tool calls, writes, time, tokens). | I-2 | HELD for turns/tool-calls/writes/wall-clock (`soul-agent-core`: `AgentConfig::{max_turns,max_tool_calls,max_write_operations,max_wall_clock_secs}` enforced in `run_task`'s turn loop and tool-dispatch loop — over-budget tool calls are refused per-call with a `BLOCKED:` result, and the wall-clock budget aborts the run; `agent_config_default_has_sane_budgets`, `new_agent_starts_with_zeroed_budgets_and_no_task_start`). Token budget not yet wired — follow-up. |
| INV-PLAN-3 | Emergency stop denies new side effects and is durable across restart. | I-2 | HELD (`soul-agent-core::emergency_stop::EmergencyStop` — a file-backed latch checked at `run_task` entry and on every turn/tool-dispatch iteration; durability across restart is by construction, since the check is a filesystem read with no in-memory state to lose, not an `AtomicBool`; `trip_does_not_survive_only_in_memory_a_fresh_handle_sees_it`, `run_task_refuses_to_start_when_emergency_stop_already_tripped`, `run_task_starts_normally_when_emergency_stop_untripped`, `trip_emergency_stop_trips_latch_and_aborts_running_flag`) |
| INV-PLAN-4 | Post-execution learning signals (global error, reward) are derived from measured task outcomes, not fixed constants, and materially different outcomes yield different values. | O | HELD (`soul-agent-core::{update_global_error,calculate_reward}` previously ignored their `task`/`result` parameters — `_task`/`_result` unused, six error components and three reward components were hardcoded literals (e.g. `let prediction_error = 0.1;`, `0.8, // quality score (simplified)`), so `global_error`/`total_reward` were identical across every execution despite feeding `update_policy`'s `policy_evolution` update. Now derived from real signals actually measured during the run: success/failure, `turn`/`max_turns` ratio, `repair_count`/`tool_call_count` ratio, `consecutive_failures`/`max_consecutive_failures` ratio, `soullink_autonomy::error_metrics::GoalError`/`UncertaintyMetric` word-overlap similarity between `task` and `result`, and `soul_critique::quick_critique`'s quality score (the same scorer already used for DPO pair scoring elsewhere in `run_task`, so no new heuristic was introduced). All components clamped to `[0.0, 1.0]` per the finding's residual-risk warning about `policy_evolution` stability. `global_error_diverges_between_success_and_failure`, `global_error_reflects_repair_and_consecutive_failure_signals`, `calculate_reward_diverges_between_rich_and_empty_result`, `calculate_reward_quality_varies_with_result_richness_not_a_fixed_constant` (isolates the quality axis from the success/failure axis). Residual: "social"/"information" reward terms have no real multi-agent trajectory data available in a single-agent `run_task` call, so they reuse the same measured success/goal-alignment/quality signals rather than fabricating unrelated data — documented in code, not claimed as true multi-agent social learning.) |
